# Цикл разработки

- В начале запускаешь hot-reload сборку если она есть, иначе после разработки.
- Выполняешь разработку в режиме [](#dev-режим-разработки).
- Проверяешь сборку по hot-reload.
- Если ошибка - исправляешь пока не заработает

# Dev-режим

**Входные данные:**
- `project_dir` - корневая директория репозитория

**Задача:** Разрабатываем `dev` версию приложения

**Требования:**
- Храни файлы разработки, логи, временные данные и артефакты сборки внутри `project_dir`. Разрешено использовать штатные локальные API платформы и библиотек, — даже если система физически хранит их данные вне `project_dir`. Не записывай файлы за пределами `project_dir` напрямую.
- средство разработки с hot-reload должно переживать аварийное завершение запускаемого приложения, включая принудительное завершение процесса операционной системой, и автоматически восстанавливать цикл разработки; штатная остановка пользователем должна завершать его
- Настрой логирование согласно [](#логирование).

**Принципы:**
- работка с высокой поддерживаемостью кода:
    1. **Модульность (SRP):** одна сущность — одна задача. Изменение логики касается только одного файла.
        - Связанные файлы одного модуля (реализацию, тесты и вспомогательный код) размещай рядом в отдельном каталоге; код, используемый несколькими модулями, выноси в общий модуль.
    2. **Слабая связанность (DI / интерфейсы):** зависимость от абстракций, а не реализаций. Легко подменять компоненты.
    3. **Простота (KISS, YAGNI, DRY):** минимум избыточных абстракций, реализация строго текущих требований, единый источник правды.
    4. **Автотесты (Unit / Integration):** защита от регрессии при рефакторинге и доработках.
    5. **Строгая типизация и контракты:** компилятор ловит ошибки до рантайма (TypeScript/Rust, схемы данных).
    6. **Читаемость (Clean Code):** самодокументируемый код, говорящие имена, ранние выходы (`guard clauses`), плоская структура.
    7. **Постоянный рефакторинг:** исправление техдолга сразу по ходу работы («правило бойскаута»).
- код не должен быть мудренным, задачи простые, а их реализации прямые, минимальные и лаконичные

# Логирование

- В dev пиши логи в `{project_dir}/logs/`; в release храни их в памяти процесса (буфер до 2 МБ).
- Кнопка `Скопировать логи` читает логи из текущего хранилища.

# Стадии развития приложения

## Прототип.
Важный приоритет в выборе инстурментов:
- минимальное время итерации разработки: быстрое применение изменений, сборка и запуск

---
### Пояснение

Выбираем язык TypeScript — **один из самых быстрых в: изменил код → как можно быстрее увидел изменение в работающем прототипе**.

Из рантаймов TypeScript самые популярные:
- Браузер / PWA — не фреймворк, самая массовая основа
- React Native — ~120k
- Electron — ~120k
- Tauri 2 — ~100k

Оцениваем каждую на кроссплатформенность и системную интеграцию:
- Браузер / PWA — **НЕТ** — нет доступа к ОС: работает только в песочнице
- React Native — **ДА** — ПК и Android, но на ПК менее зрелый
- Electron — **ДА** — только ПК; для Android нужна отдельная оболочка (Capacitor)
- Tauri 2 — **ДА** — ПК и Android, интерфейс на TypeScript, но ядро на Rust

---

Тезисы:
- большая поддерживаемость кода - быстрая разработка

Итоговый выбор:
- TypeScript — быстрая сборка, быстрая разработка
    **Для высокой поддерживаемости кода**:
    - React — Из-за большого числа интерактивных компонентов и обработчиков событий: компонентная модель и декларативное управление состоянием упрощают сопровождение интерфейса и переносят работу с DOM на более высокий уровень абстракции.
    - SCSS — Формат исходников стилей; используй переменные и умеренную вложенность для группировки стилей компонентов. Избегай глубокой вложенности селекторов.
- Vite — мгновенное применение изменений в интерфейсе
- Tauri 2 — быстрая сборка и запуск.
    Пояснение: Основная логика на TypeScript; Rust только для недоступной из TypeScript системной интеграции, чтобы минимизировать время компиляции

### Особенности разработки на выбранном стеке

На ПК панель и оверлей прототипа работают в отдельных окнах Tauri и обмениваются событиями. Для проверки рендера без участия нативных окон открывай существующие представления в браузере и обеспечивай необходимую синхронизацию между ними.

### Android

На Android `SpeechBubbleService` показывает плавающий оверлей через AccessibilityService при активном поле ввода и открытой клавиатуре. Используй общий с ПК HTML/CSS/JS записи и редактора в WebView; Kotlin — хост оверлея и системные операции. Вставляй текст через Accessibility API, сохраняя выбранную пользователем клавиатуру.

- Автосборка на Andoid это: сборка и запуск на устройстве
- При первоначальной настройке Android после установки SDK/NDK выполни в `prototype` команду `pnpm tauri android init`.
- Для разработки запускай из `prototype` команду `pnpm watch:all` — ПК и Android вместе, либо `pnpm android:watch` — только Android.
- Храни разрешённые устройства в `.android-tools/devices.json` в формате `[{"serial":"…"}]`; не дополняй список автоматически.
- Для подключений из `adb devices` получай `ro.serialno` через `adb -s <подключение> shell getprop ro.serialno`. Устанавливай и запускай приложение только при совпадении с сохранённым `serial`.
- Реализуй в скрипте параллельную идентификацию устройств, установку и запуск приложения независимо для каждого устройства.
- На одном устройстве запускай один раз, предпочитая USB. Используй текущее подключение; Wi-Fi обнаруживай через mDNS после предварительного сопряжения с ADB.
